# Native Crew applications: experience contract

Status: navigation and content approved through `a2d70102`; connection and device-access specification added for review on 2026-10-05 by `native-connection-ux`. iOS, macOS desktop, and Linux desktop are required together. The applications use native platform UI, with no React Native or webview wrapper. This document defines experience and acceptance, not an implemented or built application. Connection screens below use the approved gateway contract at `0a50c4ca`; platform bindings and exclusive source ownership use `native-platform-contract` at `c047fdc1`. Neither document proves a working application. Apple verification is deferred by the operator to an available Apple runner; that does not block source implementation.

The source baseline is `6049cdf63e36e303327235834f23a798aa5a82c1`, including the approved neutral dashboard, executing-first current work, and individually inspectable Waiting cards. [The web design](web-revamp.md#signoff) remains the appearance and capability reference; the native work does not reopen its deferred scope or spend its P1–P4 budget. The public website is outside this contract.

## Purpose and delivery boundaries

An operator must be able to understand current work, answer a question, inspect the evidence, and take an existing action without losing workspace identity. On a phone, prioritize reading and responding. On a desktop, keep relationships, lists, and evidence visible together where space permits. Capability is shared; screen composition adapts to the platform.

The required journeys are:

1. Enter an authenticated connection through an approved native entry path, identify its host/workspace, and distinguish a live team from an unavailable one.
2. Find the executing task of an agent, inspect another Waiting task, and return without changing execution or selection accidentally.
3. Read a question and send a suggested or written answer; read a message and follow its parent or loaded replies.
4. Investigate a blocked agent through current work, problems, events, transcript, diff, and terminal.
5. Send an agent message or a broadcast, submit an explicit terminal prompt, and use existing agent/team controls with the same confirmations.
6. Read token/context/quota reporting, distinguish missing reports from zero, and continue or restart agents at a limit.
7. Survive disconnection, workspace switching, application backgrounding, and reopening with honest freshness and preserved navigation.

These are dashboard/operator journeys. The existence of another `Call` variant does not add it to the native UI. Creating/editing a team, creating or reassigning tasks, adding/removing agents, new task/message filters, cost estimation, durable usage history, background push notifications, and cloud account management need separate scope. Existing CLI workflows remain available outside the application. A native client must not silently become an orchestrator or expose agent-only RPCs.

## Information architecture

Use five persistent destinations: **Team, Tasks, Messages, Events, Usage**. Messages gives the existing message bus a first-class destination on small screens; it does not introduce a new messaging service. Keep the selected workspace in every destination's navigation context. Settings, connection management, appearance, and Help belong outside this destination set. Compose is an action, never a sixth tab.

Do not place five destinations inside a horizontal inspector segment. Inspector sections are subordinate to the agent. Do not display multiple full-width connection, warning, quota, and question sheets at once: keep a compact status area and open the chosen details on demand. Existing sandbox/socket/VCS warnings remain visible and readable; a question indicator names the asker and offers Answer. Connection and workspace availability remain separate facts.

Apple's [tab-bar guidance](https://developer.apple.com/design/human-interface-guidelines/tab-bars) supports labelled, persistent destinations and separates navigation from actions. Its [split-view guidance](https://developer.apple.com/design/human-interface-guidelines/split-views) supports visible selection and compact-width collapse. GNOME's [navigation](https://developer.gnome.org/hig/guidelines/navigation.html) and [sidebar](https://developer.gnome.org/hig/patterns/nav/sidebars.html) patterns support equivalent pages and frequent movement among dynamic locations. These sources were checked on 2026-10-05; the five destinations and their content are Crew-specific decisions.

### Layout and visual language

Use native system type styles, local system monospace for identifiers/evidence, and native symbolic icons with accessible names. On iOS, body copy follows the platform body text style and Dynamic Type. Desktop metadata can be denser, but essential state and task titles must remain readable under system text enlargement. Avoid importing the web's fixed virtual-row geometry: native list rows must grow with text and accessibility settings.

Carry the approved semantic colour roles into each platform adapter. App-owned dark canvas/panel/raised surfaces use neutral gray/black (`#121212`, `#1a1a1a`, `#242424` are the web reference), with blue general actions and selection accents. Light appearance retains its warm neutral reference and green action accent. Status, runtime identity, VCS, and the four labelled usage series retain their separate meanings. Do not tint structural surfaces green or use a runtime colour as health. Native system controls and high-contrast settings take precedence over pixel matching. Selection has a persistent marker independent of hover; keyboard focus remains independently visible.

A compact phone shows one reading pane. A desktop shows a split only when the main content and inspector both fit at the current text scale; otherwise it uses navigation, not overlapping panes. Keep long prose within a comfortable reading width on wide windows. Code, diff, terminal, and graph can pan within their own regions; surrounding navigation must stay visible. Do not automatically refit a graph after every push or while the operator is navigating it.

[GNOME's adaptive guidance](https://developer.gnome.org/hig/guidelines/adaptive.html), checked on 2026-10-05, recommends constrained-first layouts, lists, and retained functionality across window sizes. Native acceptance includes 1024×600 logical desktop content, narrow/tiled desktop windows, and small iPhone portrait/landscape; these are verification targets, not web breakpoint reuse.

## Actions and confirmation parity

Buttons, menus, shortcuts, and slash commands invoke one shared semantic action. State changes follow daemon acknowledgement/pushes; a pending action is not a claimed successful mutation. The UI checks current target/workspace availability before sending and renders the daemon's explanation on failure. A target change invalidates an open confirmation rather than redirecting it.

The full operator action set below applies to the local desktop adapter. On gateway connections, each action is conditional on the device grant that `native-gateway-contract` defines. Read is the default; Control and Terminal are separate, explicit host-side grants. Selected-workspace access alone does not imply terminal input, Kill, or Stop team authority. The exact method-per-tier table belongs to `notes/native-gateway.md`, not this UX contract. Render an unavailable action with a useful reason inside an authorized workspace, and never infer permission from the platform, a visible entity, or an open confirmation. Do not expose the names or metadata of ungranted workspaces.

Grant copy must explain existing agent host authority for **both Control and Terminal**. Control includes messages and answers that can direct agents to act with their existing host permissions; it is not limited to administrative buttons. Workspace grants restrict Crew access and do not create an OS sandbox or confine an agent's filesystem access to that workspace. Do not put this disclosure only beside Terminal or imply that a Control grant removes those risks. The connection flow below applies this requirement without adding an agent-action confirmation.

| Action | RPC or current implementation | Native behaviour |
| --- | --- | --- |
| Message / broadcast | `Send`; `web/src/app.ts::send` | Show recipient and workspace. Keep draft on failure. A closed connection after an in-flight send may retry once with the **same message ID**, as the web does; do not manufacture a fresh message or queue arbitrary offline sends. |
| Answer | `Answer`; `app.ts::answer` | Suggested/written answer remains explicit. Preserve question identity and restore it on failure. No background automatic answer. |

The confirmation set is exactly the existing one in `web/src/views/dialogs.tsx::ConfirmDialog` and `crates/crew-tui/src/input/dialogs.rs`: Kill, Restart fresh, Restart paused at limit, Stop team. The table does not authorize additional confirmations or removal of these four. Revalidate the named target at confirmation time. Escape/Cancel dismisses and restores focus. An unavailable connection cannot approve a mutation merely because the dialog is already open.

Slash commands retain `crew_core::util::slash_command` / `web/src/commands.ts` semantics: a leading command is never accidentally sent as a message; unknown commands retain the draft with a useful explanation. Native menus expose the same common actions without requiring command knowledge. Terminal, text-editing, and assistive-technology keys take precedence over single-key dashboard shortcuts.

## Connection, setup, and lifecycle

The authority for these screens is [native-gateway.md](native-gateway.md) at `bd608ce0d9efaad442611db482e865c02785c3fd` plus `0a50c4ca43cc67947ca381177c83cfead1774920`, approved by `native-gateway-contract`. Its endpoint, TLS verification, device key, enrollment, method policy and revocation rules are normative. This section supplies screen order, copy and recovery for those rules; it introduces no transport, credential, permission or remote administration mechanism. Implementation and live acceptance are still required.

The browser rule remains unchanged: **never paste or scan `crew web` output into an app or page**. Native setup accepts only the gateway's public host profile and independently verified trust material. That profile is not a browser address/code handoff. There is no browser-code field, QR scan, secret clipboard import, SSH-account setup or universal-link credential flow. Host/Origin do not authenticate a native client. The delivered loopback dashboard is not reachable from an iPhone; adding a profile does not start or expose a server.

### Failure, recovery and lifecycle copy

A stored expiry can be labelled **Saved access expiry**, not used to infer a remote diagnostic. Full versions are shown only for authenticated protocol mismatch. Exact equality remains required (`rpc.rs::PROTOCOL_VERSION`; web mirror `web/src/protocol.ts::PROTOCOL`).

Nothing was approved by this attempt.” | Never reuse an expired/consumed code. Five failed local comparisons consume that intent; restarting is an explicit new request/window. Generic remote refusal must not invent the host's precise reason. |
| Canceled before approval is known | Close the enrollment channel; show “Request closed.” If the connector can confirm no commitment, return to Connections. | Closing a UI is not proof that a concurrent host approval was undone. No silent replacement request. |
| Lost approval reply / cancellation race | “The connection closed before approval was confirmed here. The host may have approved this device. Reconnect to check, or revoke it at the host.” **Reconnect to check** uses the same key and verified profile. | No success claim, duplicate device, automatic key rotation or promise that no host grant exists. A local `Canceled` outcome and `OutcomeUnknown` retain their distinct meanings. |
| Auth unavailable / known expired or revoked access | Generic failure: “Device access is unavailable. Check with the host operator.” Authenticated expiry/revocation may be named precisely. **Connection details** / host enrollment instructions. | No key-existence leak, trust reset or automatic renewal. Renewal/replacement requires a new key and explicit host-selected grants; previous powers do not carry over. |
| Connecting / reconnecting / suspended | “Connecting” or “Reconnecting”; retained data says **Last known**, with last synchronization time where known. **Disconnect** remains available. | No live badge or action until authentication, current grants/listing and snapshot synchronization. No queued offline mutations or terminal-byte replay. |
| Running / stopped / unreachable / incompatible | Live only after the barrier snapshot. “Team is not running,” “Team cannot be reached,” or “This app and host use incompatible versions. | Not permitted / removed / no longer granted | Authorized action shows its missing power. A removed or denied route shows “This workspace is no longer available to this device” and **Back to workspaces**, without its now-ungranted name/path/count. | No request sent from a disabled action; no hidden failure disguised as loading. Grant loss cancels open confirmations and terminal input, removes denied selector entries and purges that scope's evidence/drafts when learned. |
| Host revocation in progress / complete | Trusted host console says **Revoking access** until draining completes, then **Access revoked** only after success. Device sees access end and returns to safe connection/workspace context. | Already accepted commands may finish. Do not promise rollback or deletion of data a disconnected device already received. | Service stop / runtime-state loss | Normal stop: “Native service is unavailable”; reconnect can use a retained valid profile after restart. Missing host state does not restore grants, import authority from another directory or silently trust a new endpoint. |
| Detail read or terminal failure | Keep the current authorized entity summary with local loading/empty/error text. **Refresh** retries that read when live. Terminal distinguishes ended, detached, overflow, unsupported and disconnected. | No stale response populates another entity/scope. No fallback transcript is represented as successful interactive-terminal acceptance. |

**Disconnect** closes this application's channels and keeps the profile/key for later use; it neither revokes access nor stops the team. **Remove from this app** explicitly says “Removes this profile and retires this app's device key. Host access remains until revoked or expired.” It performs local retirement only, through the approved key service. Before that action, show **How to revoke access** so an operator can first revoke the named device at the trusted host console. Host revocation names the device and all affected workspace grants; removing one workspace grant leaves the device's other grants intact. There is no remote Revoke button disguised as Disconnect. None of these local settings actions adds a confirmation to the existing four agent/team actions.

On iOS foregrounding, and after any suspended native host resumes, treat retained data as stale until reauthentication, refreshed authority/listing and a new snapshot barrier complete. Preserve local navigation and authorized drafts across ordinary connection loss; learned revocation purges the affected scope as required by the platform contract. Do not durably cache private evidence as part of this UX task. Routine preferences contain public profile/presentation fields only. Device private keys remain in the OS credential service, or explicitly chosen supported memory-only storage; no credential-store handle, upstream token, proof, signature or secret reaches view records, diagnostics, analytics or screenshots. The accepted comparison code is temporary ceremony UI, never a log or routine settings value.

### Setup accessibility

Keep every field labelled and every failure associated with its field or status region. After an explicit failed submit, focus the first invalid field or error summary; background connection updates do not move focus. Announce enrollment acceptance, expiry and completion once, not every countdown tick. Keep all four comparison groups and the full fingerprint available as selectable native text with separate accessible group labels; character-by-character reading must preserve leading zeroes and letter/digit distinctions. Never require memorizing a code hidden on a previous screen. Back navigation must not accidentally submit, approve or generate another key. Screen-reader and keyboard tests must include the trusted host-console comparison, not just the app.

iOS uses the existing 44pt targets, largest Dynamic Type and VoiceOver requirements; the primary action and Cancel remain available with the keyboard open. macOS uses VoiceOver, Full Keyboard Access and standard text selection; Linux uses keyboard traversal, native screen-reader roles, large text and on-screen keyboard. On all three, long labels/endpoints wrap without truncating the host identity needed for verification; fingerprint and comparison groups wrap only between groups. Approval or expiry cannot silently drop focus to an empty page. After access loss, focus the safe explanation, then offer the remaining authorized workspace list or Connections. These are acceptance requirements, not a claim that native authentication accessibility has been verified.

## Accessibility and native interaction

Each platform must provide a complete list/detail path independent of graph geometry. VoiceOver on iOS/macOS and the Linux screen reader must expose entity ID, status, current task, selection, and available actions in a useful order.
